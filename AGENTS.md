# Reboot Archive — Agent Guide

## Purpose and scope

Reboot Archive is a static, curated archive and resale platform for vintage Apple technology. It gives restored, collectible, and well-kept devices a considered second chapter through product photography, practical condition information, and accurate design history. Keep it recognisably an archive and collection—not a generic electronics marketplace.

The site is plain HTML, CSS, and JavaScript, suitable for static hosting. The local publishing tool is `inventory_manager.py`. The repository's existing architecture is intentional: extend it unless a requested task clearly requires a change.

## Repository map and ownership

- Root `*.html` files are the hand-maintained site pages.
- `assets/css/` contains page and listing stylesheets; `assets/js/` contains page-specific interactions.
- `navigation.css` and `navigation.js` are shared navigation assets. `listing-search.css` and `listing-search.js` are the shared collection-search assets.
- `inventory/<product-id>/listing.json` is the source of truth for a listing. `description.txt` is its plain-text companion; media and an optional condition-report PDF live beside it.
- `inventory/<product-id>/listing.html`, `inventory/catalog.json`, and the inventory grids in `collections.html` and `archive.html` are generated by `inventory_manager.py`.
- Do not remove or rename `<!-- INVENTORY:START -->` / `<!-- INVENTORY:END -->` in `collections.html`, or `<!-- ARCHIVE:START -->` / `<!-- ARCHIVE:END -->` in `archive.html`.
- `inventory/sequence.json` controls the next `RA` identifier. Preserve identifiers, folder names, and relationships.

Do not manually edit generated listing pages or generated catalogue/listing-grid output when the same result can be made through the source listing data or generator. If a generator change is necessary, retain its current output structure and regenerate affected output deliberately.

## Design and front-end standards

- Preserve the established editorial, Apple-inspired visual identity: restrained typography, deliberate whitespace, warm neutral palette, muted green/grey tones, and the existing rust accent. It should feel considered and content-led, not like a copy of modern Apple.com.
- Prefer the existing typography, CSS custom properties, class names, shared navigation, layout patterns, and responsive conventions over new visual systems or one-off variants.
- Use semantic HTML5 and a logical heading hierarchy. Use `main`, `header`, `nav`, `section`, `article`, `footer`, lists, and definition lists where they accurately express content.
- Keep styling in external CSS files. Do not add inline `style` attributes or embedded `<style>` blocks. Reuse classes and shared rules instead of repeating declarations or styling via unnecessary IDs.
- Keep HTML, CSS, JavaScript, JSON, Markdown, and generated markup consistently formatted and readable. Do not trade readability for fewer lines.
- Maintain responsive behaviour for desktop, tablet, and mobile. Avoid decorative effects, animation, shadows, gradients, or new dependencies unless they are clearly needed and fit the established design.
- Keep site navigation and shared page chrome consistent. Do not duplicate or bypass existing navigation behaviour.

## Accessibility and metadata

- Provide concise, descriptive `alt` text for meaningful images; use empty `alt` text only for genuinely decorative images.
- Preserve keyboard usability, visible focus states, labelled controls, sensible reading order, and sufficient colour contrast. Do not communicate meaning with colour alone.
- Give every user-facing page a unique, accurate `<title>` and meta description. Retain responsive viewport metadata, canonical URLs where the site already uses them, and meaningful heading hierarchy.
- Use descriptive filenames and avoid duplicate metadata across generated listings. Ensure external links that open a new tab include appropriate safety attributes.

## Historical and listing accuracy

- Never invent product specifications, release dates, generation names, model numbers, condition claims, repair history, included accessories, provenance, or test results.
- Keep Apple product names, generations, dates, and model numbers accurate. Do not infer specifications from visual similarity or from a related model.
- Clearly distinguish confirmed facts from uncertain, conflicting, incomplete, or unverified information. Flag uncertainty to the requester rather than presenting a guess as fact.
- Preserve historical authenticity: do not modernise historical copy, imagery, terminology, or presentation in a way that misrepresents the original product.
- Treat product descriptions and condition notes as factual records. Do not overwrite manually maintained material with generated or assumed content.

## Python, data, and generated pages

- Follow the configured Python baseline: Python 3.11, PEP 8, 100-character line length, double quotes, descriptive names, small focused functions, and appropriate error handling.
- Keep file writes safe and non-destructive. Validate inputs before modifying data; preserve backwards compatibility with the existing listing schema unless a schema migration is explicitly requested.
- Do not delete listings, assets, condition reports, product data, or identifiers without explicit permission. Do not silently rewrite user-maintained data.
- Generated listings must use the same semantic structure, external CSS, shared navigation, metadata, accessibility practices, and formatting quality as hand-maintained pages.
- When modifying `inventory_manager.py`, ensure it continues to generate formatted HTML, safely escapes content, and updates only the intended marker-delimited grids.

## Working method

1. Inspect the relevant implementation, existing patterns, and current Git status before editing. Do not assume a file's role or a feature's behaviour.
2. Make the smallest targeted change that fulfils the request. Extend existing components and utilities rather than recreating them.
3. Preserve existing functionality, architecture, data, and design decisions when uncertain. Do not remove something merely because it appears redundant.
4. State material assumptions and explain any architectural or schema change in the handoff.
5. Run checks that match the change, then inspect the result. Useful repository checks include `npm run format:check`, `npm run lint:python`, and the relevant page or generated listing output. Use `npm run format` or `npm run format:python` only when their scope is understood, because they may rewrite many files.
6. Report exactly what was changed and what was verified. Never claim completion, visual correctness, or successful generation without verifying it.

## Git and project safety

- Preserve all uncommitted work. This repository may contain deliberate local changes; do not overwrite, discard, reset, clean, stash, or reformat unrelated files.
- Keep changes confined to the request. Do not introduce dependencies, broad refactors, generated-file churn, or repository restructuring without a clear need and explanation.
- Never use destructive filesystem or Git operations, delete project directories, rewrite history, or force-push without explicit permission.
- Do not commit secrets, credentials, private URLs, or personal data.

When in doubt, preserve existing functionality and architectural decisions rather than changing them based on assumptions.
